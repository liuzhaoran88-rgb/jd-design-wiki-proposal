# Toast · 文案规则

> Toast 的文案是「**用户在 2-3s 内必须读完并理解**」的内容。每多一个字都是负担,字数硬约束。

---

## 1. 字数硬约束(max-length)

| 形态 | 字符上限 | 推荐范围 |
|---|---|---|
| 单行(形态 A/B) | **12 字符** | 4-8 字符最佳 |
| 双行(形态 C)主文字 | 12 字符 | 4-8 字符 |
| 双行(形态 C)副文字 | 24 字符 | 12-18 字符 |

**判断标准**(从 Relay 源稿):*"保证显示时间内的可读性"*——按中文阅读速度 ~5 字 / 秒,2s 上限即 10 字,留 2 字冗余 = 12 字硬约束。

超出 12 字,**截断不是出路**——重新设计文案,或改用 Dialog / NoticeBar。

---

## 2. 句式约定(grammar)

| 类型 | 句式 | 示例 |
|---|---|---|
| `success` | 动词 + 「成功」 | 关注成功 / 收藏成功 / 发布成功 |
| `error` | 动词 + 「失败」 | 发送失败 / 上传失败 / 支付失败 |
| `warning` | 动词 + 状态描述 | 网络异常 / 余额不足 / 已达上限 |
| `loading` | 动词 + 「中」 | 加载中 / 提交中 / 上传中 |

**禁止句式**:
- ❌ 完整句:"您的订单已提交成功,稍后将为您配送"(超长 + 重要信息错配)
- ❌ 单字:"完成"(语义不足,用户不知道完成的是什么)
- ❌ 反问 / 疑问:"是否要重试?"(toast 不响应交互,反问无意义)

---

## 3. 不要混入重要信息

> 来自 Relay 源稿:*"e. 不适用于展示大量文案、重要信息"*

**重要信息的判断**:

| 用户需要... | 应该用 |
|---|---|
| 做决策(是否重试 / 是否取消) | **Dialog** |
| 记录数字(订单号 / 兑换码) | **Sheet 或专门页面** |
| 复制文本 | **不用 Toast**(toast 不可选中复制) |
| 再次查看 | **持续提示(NoticeBar)** |

Toast 的本质是「过眼烟云」,任何"用户错过就找不回"的信息都不该在这里。

---

## 4. 多语言适配

- 英文 / 俄文 / 日文等语言,字符数限制 → **24 字符**(对应中文 12 汉字的视觉宽度)
- 阿拉伯语 / 希伯来语等 RTL 语言:容器布局自动镜像,图标位置反转
- **不能用 emoji**(部分系统渲染异常 + a11y 屏幕阅读器播报不可控)

---

## 5. 文案 owner 链路

- **PM / 产品** 提需求时给出文案初稿
- **内容运营 / UX writer** 终审,确保统一句式 + 字数
- **前端** 不得擅自修改文案(包括拼接 i18n key)——所有文案必须可被 search 到源稿

---

## 与 Token 的边界

文案不进 Token——文案是业务上下文,不是设计基础。
